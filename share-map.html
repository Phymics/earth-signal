AI 轻应用生产地图

从一个点子，到可访问、可播放、可自动更新、可推送的小产品。

01

点子成型：从一个日常想法开始

先把小想法压缩成一句产品句子，明确最小闭环。

ChatGPT产品定义范围收敛

做了什么 / 解决了什么

把一个很小的想法先收敛成一句话：每天自动捕捉一条世界新闻，生成 1 分钟左右可以收听的内容。这个阶段解决的不是技术问题，而是产品方向问题：先明确“我要做什么”，而不是一上来就陷入工具选择。

工具选型 / 为什么选

主要使用 ChatGPT 做想法收敛和产品定义。也考虑过直接写飞书文档、画原型、做 PPT，但最终先用对话把需求讲清楚，因为最快、成本最低，也最适合从一个模糊念头起步。

当时卡点 / 怎么解决

当时的卡点是：点子很容易发散，可能变成新闻站、播客站、AI 助手、资讯聚合器。最后解决方式是把范围压小：只做“一天一条信号 + 1 分钟收听”，先形成一个最小闭环。

可演示入口

建议现场用一句话带过，不需要展开太多。可以展示最初的产品定义文字，或者口述：“我不是先写 PRD，而是先把想法压缩成一句产品句子。”

02

第一个 Demo：先让产品长出来

先做出能看的网页，再围绕真实页面继续判断和修改。

CodexHTML/CSS/JS可运行 Demo

做了什么 / 解决了什么

用 Codex 把想法快速变成第一个可以看的网页 Demo，包括首页、每日新闻播客入口、内容卡片、播放器雏形。这个阶段解决的是“从 0 到可见”的问题：先让产品长出来，再围绕真实页面继续判断和修改。

工具选型 / 为什么选

主要使用 Codex + HTML/CSS/JS 单文件。考虑过 Figma、Axure、飞书原型、手动画图，但最终先让 Codex 直接写页面，因为时间紧，而且网页 Demo 可以直接变成后续真实产品，不只是静态图。

当时卡点 / 怎么解决

当时的卡点是：如果先做高保真原型，很可能做完还不能运行；如果先写完整需求，又会太慢。解决方式是先让 Codex 生成可运行页面，用真实界面代替抽象描述，再一轮轮改。

可以打开本地或公网的 Earth Signal 首页，展示“第一个可看的形态”。如果还保留 index_v2_backup.html / index_v3_backup.html，可以作为阶段性成果截图；如果不展示备份文件，就展示当前页面并说明它是迭代后的版本。

03

本地运行：建立“改完就能看”的验证闭环

用本地 HTTP 服务让每次修改都能马上验收。

Python3localhost本地验证

做了什么 / 解决了什么

用 Python3 在本地启动 HTTP 服务，让 index.html 可以在浏览器里真实运行。这个阶段解决的是验证效率问题：每次 Codex 改完后，不是凭感觉判断，而是马上打开页面看效果。

工具选型 / 为什么选

使用 python3 -m http.server 8000。这个方案不需要额外安装复杂服务，不需要配置后端，也不依赖平台，适合静态页面快速验证。相比完整前端工程，它更轻、更快。

当时卡点 / 怎么解决

当时的卡点是：直接打开 html 文件和通过本地服务访问，体验并不完全一样，后续音频、数据路径、相对路径都需要更接近真实部署环境。解决方式是统一用 localhost:8000 访问，形成标准验证动作。

可演示入口

现场可以演示：
cd /Users/phymics/Desktop/codex
python3 -m http.server 8000
然后打开：http://localhost:8000/
也可以展示终端截图，说明这是每次改完后的基础验收入口。

04

手机局域网访问：验证真实移动端体验

电脑可用不等于手机可用，用真机验证移动端细节。

局域网 IP手机浏览器真机验收

做了什么 / 解决了什么

把本地页面通过局域网 IP 给手机访问，验证真实移动端体验。这个阶段解决的是“电脑可用不等于手机可用”的问题，尤其是页面宽度、按钮尺寸、音频播放、图标显示等移动端问题。

工具选型 / 为什么选

使用 Mac 本机局域网 IP + 手机浏览器访问。没有上来就依赖公网，也没有复杂部署，原因是速度最快，可以马上验证手机端真实效果。

当时卡点 / 怎么解决

当时遇到过手机打不开的问题，后来发现流量可以打开、公网路径也要区分；也遇到过手机端播放图标显示成 emoji 的问题，比如播放按钮变成蓝色系统 emoji。解决方式是改成 CSS 绘制图标，不再依赖特殊字符。

可演示入口

可以现场展示手机访问页面，或者放截图：手机端首页截图、手机端播客页截图、播放按钮从 emoji 改成 CSS 图标前后的对比截图。如果现场演示，可以让大家看到同一个页面在手机上的真实效果。

公网发布：从 Netlify 拖拽到 GitHub Pages

从快速临时预览，升级为可持续自动发布链路。

Netlify DropGitHub Pages持续发布

做了什么 / 解决了什么

先用 Netlify Drop 把本地 Demo 快速拖拽上线，验证“别人能不能打开”。后面切换到 GitHub Pages，作为正式公网发布方式。这个阶段解决的是公网访问能力，让作品从“只有我电脑能看”变成“任何人都能打开”。

工具选型 / 为什么选

考虑过 Netlify、Vercel、GitHub Pages。Netlify Drop 的优势是最快，适合早期临时预览；Vercel 登录和流程对当时来说更有阻碍；GitHub Pages 最终更适合和 GitHub 仓库、自动更新、Actions 串起来，所以后续选择 GitHub Pages 作为正式链路。

当时卡点 / 怎么解决

当时的卡点是：临时发布很快，但如果每天自动更新，就不能靠手动拖拽文件。解决方式是先用 Netlify Drop 验证公网访问成立，再迁移到 GitHub Pages，让代码仓库、自动任务和公网页面形成一个持续发布链路。

可演示入口

可以展示 Netlify Drop 页面或当时拖拽发布截图，如果还找得到；也可以展示 GitHub Pages 公网页面和 GitHub Actions 触发 Pages build 的截图。现场可以说：Netlify 是验证“能不能给别人看”，GitHub Pages 是解决“能不能持续自动更新”。

内容生成：从 Mock 到真实 RSS

从静态文案升级为每天变化的真实内容输入。

MockRSSPython3JSON

做了什么 / 解决了什么

从最早的 mock 文案，升级为抓取真实 RSS 新闻源，再用 Python3 进行候选新闻抓取、筛选、总结、结构化，最终生成 today-podcast.json 和 history-podcasts.json。这个阶段解决的是“内容从哪里来、如何每天变化”的问题。

工具选型 / 为什么选

使用 Python3 抓取和处理 RSS，使用公开 RSS 新闻源作为内容来源，生成 JSON 给前端读取。选择原因是：RSS 公开、稳定、低成本；Python 适合快速写抓取和处理脚本；JSON 适合静态网页直接读取，不需要后端数据库。

当时卡点 / 怎么解决

当时的卡点是：页面一开始只是静态内容，看起来像 Demo，不像每天真的会变化的产品。后来引入 RSS 后，又遇到“当天可能选中同一条新闻”的情况，导致推送收到了但页面内容看起来没变。解决方式是通过日志、git show、JSON 内容核对，确认链路是通的，只是筛选结果未变化。

可演示入口

可以现场打开 JSON，展示页面内容不是写死的，而是脚本生成的；也可以展示 GitHub Actions 里 Generate daily podcast 的日志。

07

音频能力：从浏览器朗读到双语 MP3

从“能读”升级到更像播客产品的真实音频文件。

SpeechSynthesisedge-ttsMP3双语

做了什么 / 解决了什么

最早版本使用浏览器原生朗读作为兜底，但声音比较机械，也不稳定。后来升级成生成真实 MP3 文件，并支持中文 / 原文两套音频，历史节目也能和对应音频一一匹配。这个阶段解决的是“从能读，到像一个真正播客产品”的问题。

工具选型 / 为什么选

使用 edge-tts 生成 MP3。考虑过浏览器 SpeechSynthesis、在线 TTS 服务、第三方音频 API。最终选择 edge-tts，是因为它能在 Python 脚本里自动跑，生成真实音频文件，适合 GitHub Actions 自动化执行，也不需要复杂前端依赖。

当时卡点 / 怎么解决

当时的卡点是：浏览器原声朗读很机械，且不同设备体验不一致；同时只生成一份音频时，中英文切换会出现内容和音频不完全对应的问题。解决方式是生成 today-podcast-zh.mp3 和 today-podcast-original.mp3，并给历史内容建立 history 音频目录。

可以展示音频文件目录和页面里的中文 / 原文切换。现场可以演示：切到中文播放中文音频，切到原文播放英文音频。

自动化闭环：GitHub Actions + 外部服务集成 + 微信推送

定时生成、自动部署、主动推送，形成完整生产闭环。

GitHub ActionsGitHub PagesSecretsPushPlus / Server 酱

做了什么 / 解决了什么

把整个流程接进 GitHub Actions：定时触发、运行 Python 脚本、生成 JSON 和 MP3、提交到仓库、触发 GitHub Pages 部署，并通过外部推送服务把结果推送到微信。这个阶段解决的是“每天不用手动操作，也能更新和触达”的问题。

工具选型 / 为什么选

使用 GitHub Actions 做自动任务，GitHub Pages 做部署，PushPlus / Server 酱作为外部推送服务，GitHub Secrets 管理推送服务的访问凭证。选择原因是：GitHub Actions 和代码仓库天然集成，适合自动跑脚本；Secrets 可以避免把 key 写进代码；PushPlus / Server 酱适合把结果送到微信。

当时卡点 / 怎么解决

当时的卡点比较真实：一开始以为 8:30 会自动收到推送，但早上没有收到。后来排查发现定时任务没按预期出现；手动运行后，推送成功，说明整体链路是通的。之后又发现页面内容没变，是因为脚本选中了同一条新闻，不是部署失败。最终通过增加 fallback schedule、查看 Actions 日志、核对 commit 和 JSON 内容，确认链路稳定。
